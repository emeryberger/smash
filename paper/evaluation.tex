\section{Evaluation}
\label{sec:eval}

We structure the evaluation around five questions:

\begin{enumerate}
\item[\textbf{RQ1.}] How much does \sys reduce RSS on real
  applications, and what is the throughput and latency cost?
\item[\textbf{RQ2.}] How do compression algorithms compare on heap
  page data?
\item[\textbf{RQ3.}] What does each optimization contribute?
\item[\textbf{RQ4.}] How does allocator design affect page
  compressibility?
\item[\textbf{RQ5.}] How much of the benefit comes from the
  compression pipeline versus the allocator design?
\end{enumerate}

\subsection{Methodology}
\label{sec:eval:method}

We evaluate on Linux x86\_64 (Amazon Linux~2, kernel~5.10,
glibc~2.26, 4\,KiB pages, 64\,GiB RAM, 16 cores).  \sys is loaded
via \texttt{LD\_PRELOAD}; RSS is sampled via
\texttt{/proc/[pid]/statm} at 1\,s intervals.
Each configuration is run three times; we report the median.

Benchmark applications: Redis~8.0.2 (built with libc malloc),
memcached~1.6.34, RocksDB~9.8.4, SQLite~3.51.0.
Compression libraries: LZ4~1.9.4, zstd~1.5.6.

\paragraph{Memcached}
We load 500K TPC-H JSON records into memcached, then serve a hot 5\%
for 30 seconds before re-accessing cold keys.  Serve-phase
RSS drops from 287\,MiB to 136\,MiB (52\%).  Cold-key re-access
benefits from \sys prefetching adjacent pages on fault.  Throughput
is unchanged.

Fill-phase RSS is $\sim$8\% higher due to the
bootstrap allocator, page state arrays, and compression contexts.
This fixed overhead is amortized as the working set~grows.

\paragraph{SQLite}
An in-memory database with 1M records queried with random lookups.
RSS drops from 464\,MiB to 136\,MiB (71\% reduction).
Query throughput is 76K~ops/s, within 0.4\% of the~baseline.

\paragraph{RocksDB}
A 256\,MiB uncompressed block cache populated with 200K key-value
pairs.  Serve-phase RSS drops from 279\,MiB to 68\,MiB (76\%).
RocksDB's built-in compression (LZ4 or zstd) reduces
data size on disk but not in the block cache, since blocks are
decompressed on load.  \sys and RocksDB compression are
complementary: they operate at different levels of the
storage~hierarchy.

\paragraph{Redis}
We evaluate two workloads with \texttt{redis-bench\-mark}
(100K ops, 1000\,B values, 5K connections, LLAMA
config~\cite{maas2020adaptive}).
The \emph{standard} workload fills the keyspace and measures
post-cooling RSS\@.  The \emph{extended} workload deletes
50\% of keys before cooling, creating fragmentation
that lets allocators exploiting partially-filled pages
reclaim space.

Redis's event loop and background tasks (active defragmentation,
incremental rehashing, lazy-free) can keep pages warm even during
idle periods.  To achieve effective compression, we configure Redis
with minimal background activity:
\texttt{-{}-hz\,1 -{}-dynamic-hz\,no -{}-activedefrag\,no
-{}-activerehashing\,no -{}-lazyfree-lazy-*\,no}.
Disabling these tasks does not affect baseline performance: jemalloc
achieves identical RSS (333\,MiB), AUC (6656\,MB$\cdot$s), and
throughput with or without background tasks.
With this configuration, \sys achieves 36\% RSS reduction
(417\,MiB to 266\,MiB) and 16\% lower AUC (5565 vs.\ 6673\,MB$\cdot$s)
on a 200K-op workload with 2\,KiB values.

On the extended workload (SET $\to$ DELETE~50\% $\to$ cool $\to$ GET),
\sys shows \emph{negative} benefit: cool RSS increases from 333\,MiB
to 637\,MiB ($-$65\%).  DELETE operations touch all keys, causing
wholesale decompression; the partially-freed pages do not re-compress
well because the remaining live objects are scattered.
Throughput is comparable across all configurations ($\pm$5\%).

\paragraph{Root cause analysis and Redis patches}
Two specific Redis behaviors prevent effective compression.
First, \texttt{serverCron()}'s background operations---active
defragmentation, incremental rehashing, and hash table
resizing---traverse key data pages every cron tick, keeping them
warm even when no client commands are being processed.  With
\texttt{--hz\,1} and all configurable background tasks disabled,
only 0.4\% of pages reach the cold threshold because
\texttt{serverCron} still runs defrag and rehash unconditionally.

Second, \texttt{DEL} calls \texttt{getObjectLength()} to
update the keysizes histogram.  This dereferences the value pointer
into value data pages (SDS headers, dict sizes, etc.),
triggering SIGSEGV on compressed pages and causing wholesale
decompression.  Similarly, the async-delete path calls
\texttt{kvobjAllocSize()} for memory tracking, which traverses
value data structures.

We address both issues with minimal, semantics-preserving
patches to Redis (7~files, 105~lines added, 51~removed).
For the \texttt{DEL} problem, we add two write-through cache
fields to the \texttt{kvobj} header: \texttt{cached\_length} and
\texttt{cached\_alloc\_size}.  Both are updated transparently
on every call to \texttt{getObjectLength()} and
\texttt{kvobjAllocSize()} respectively, so all 58+~call sites
in Redis command handlers keep the cache current with no
modifications.  The delete path reads these cached values from
the object header (same cache line as \texttt{type} and
\texttt{encoding}) instead of dereferencing into value data pages.
Keysizes histograms and slot allocation tracking are preserved.

For the \texttt{serverCron} problem, we add an
\texttt{idle-mode} configuration option.  When enabled, Redis
tracks whether any commands have been processed in the last three
cron ticks.  During idle periods, \texttt{databasesCron()} skips
only the three operations that inherently traverse key data pages:
\texttt{activeDefragCycle()}, \texttt{kvstoreIncrementallyRehash()},
and \texttt{kvstoreTryResizeDicts()}.  All other operations
continue unconditionally: active key expiration (TTL correctness),
\texttt{clientsCron()} (client timeout enforcement),
\texttt{cronUpdateMemoryStats()} (allocator statistics), replication
and cluster heartbeats, AOF persistence, and all periodic cleanup
tasks.  When client commands resume, the idle counter resets and
all operations return to normal.

Table~\ref{tab:redis_patched} shows the results on a 50K-key
workload with 2\,KiB values.  With both patches, \sys achieves
94\% RSS reduction on the standard workload (204\,MiB baseline to
11.8\,MiB) and, critically, pages \emph{re-compress after DELETE}:
the final minimum RSS (19.5\,MiB) returns to within 65\% of the
pre-DELETE minimum, compared to a $6\times$ RSS increase without the
patches.  Total AUC drops by 84\%.

The patches illustrate a general principle: applications that
access heap data structures during idle periods interfere with
page-level compression.  Separating metadata from data---so that
bookkeeping operations read cached values in object headers rather
than dereferencing into data pages---and deferring
data-page-touching maintenance until the application is active
are sufficient to make such applications compatible with
transparent heap compression.

\paragraph{Comparison across allocators}
To confirm that compression, not allocator choice, drives the
RSS reduction, we run all benchmarks with
Mesh~\cite{powers2019mesh} as a representative alternative allocator
(Table~\ref{tab:apps_summary}).  Mesh uses external metadata and virtual-memory
remapping to merge two virtual pages onto one physical page when
their live objects do not overlap.
Mesh provides no benefit on memcached, RocksDB, or Redis
(matching or exceeding baseline RSS).  On SQLite, Mesh \emph{increases}
RSS by 85\% due to page-meshing overhead.  \sys achieves 52--76\%
reduction on these workloads via compression.
Without a compression pipeline, even Mesh's aggressive page
remapping cannot reclaim space from pages with live~objects.

\paragraph{Summary}
\sys reduces RSS by 47--76\% on workloads where data stays cold
(memcached, RocksDB, SQLite, Redis with background tasks disabled),
with negligible throughput cost ($\leq$0.4\%) and sub-10\,$\mu$s median
cold-access latency.
The benefit scales with the fraction of cold data and data
compressibility.  Compression, not allocator choice,
drives the savings: Mesh provides no benefit (and increases
RSS on SQLite), while \sys achieves consistent reductions via compression.
On unmodified Redis, DELETE workloads cause wholesale decompression,
but two small patches---caching object metadata in headers and
deferring data-page-touching maintenance during idle
periods---restore 90--94\% RSS reduction even with 50\% key deletion
(Table~\ref{tab:redis_patched}).

\subsection{Algorithm Comparison (RQ2)}
\label{sec:eval:algo}

To understand which compression algorithms are best suited to heap
page data, we compare LZ4 and zstd at several levels on
pages captured from the four application heaps.
Figure~\ref{fig:algo_compare} presents compression ratios and
Table~\ref{tab:algo_throughput} presents throughput.  \punt{WKdm, the macOS VM compressor, achieves only 1.0--1.1$\times$
on text data because its 32-bit word-granularity dictionary cannot
match byte-level patterns.  It performs adequately on binary data
(6.4$\times$ on SQLite pages).  }LZ4 achieves 4.7--12.3$\times$ compression at
$\sim$3\,GB/s.  zstd-1 achieves 1.5--2$\times$ higher ratios
(8.8--20.4$\times$) at $\sim$2$\times$ lower throughput, because its
entropy coder (FSE) captures byte-frequency skew that LZ4's
literal-copy format cannot exploit.  zstd-9 achieves the best
ratios (9--21$\times$) at lower~throughput.

\paragraph{Summary}
Heap pages compress well: zstd-1 achieves 8.8--20.4$\times$ compression
at 0.6--1.4\,GB/s, and zstd-9 reaches 9--21$\times$ on structured data at
lower throughput.  zstd-1's entropy coder gives 1.5--2$\times$ better
ratios than LZ4 at $\sim$2$\times$ lower throughput; for cold pages
that remain idle, the better ratio yields higher net~ROI\@.
These results motivate \sys's ROI-based JIT
compression: because highly compressible data is also \emph{cheaper}
to compress (higher throughput), the ROI is doubly favorable---the
model naturally selects zstd-1 for recently cold pages (where fast
compression minimizes risk) and zstd-9 for long-idle pages (where the
better ratio justifies the~cost).

\subsection{Ablation Study (RQ3)}
\label{sec:eval:ablation}

To quantify what each optimization contributes, we selectively
disable individual features and measure the change in RSS reduction.
We run each configuration across all four applications (five workloads),
each with 3 runs.  Ablation requires rebuilding \sys with different
compile-time constants; external-process benchmarks (memcached, Redis)
are run via library interposition (\texttt{LD\_PRELOAD}) against each
rebuilt library.
Figure~\ref{fig:ablation} shows the~results.

The most striking result is that enabling dictionaries
\emph{reduces} RSS savings by 5--30\,\pp across all benchmarks.
CDict objects consume 686\,KiB each at level~9, and at that
compression level, zstd's search window already captures the
patterns a dictionary would provide.  \sys therefore disables
dictionaries by default.

Disabling compression entirely ($-$45.7\,\pp average) confirms that
compression is the dominant mechanism; without it, \sys reduces to
a standard allocator with no RSS benefit beyond what the allocator
design alone provides.  The remaining optimizations---arenas, fast-only
mode (disabling zstd-9 re-compression), deferred zeroing, prefetch, and
parallelism---each contribute less than 1.5\,\pp individually.

\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{figures/ablation.pdf}
\caption{\textbf{Dictionaries and disabling compression are the
  only configurations with large impact}
  (\S\ref{sec:eval:ablation}).  Change in RSS reduction (\%)
  from default.}
\label{fig:ablation}
\end{figure}

\paragraph{Summary}
Compression is the dominant mechanism: disabling it eliminates
virtually all RSS savings ($-$45.7\,\pp).  Dictionaries are
actively harmful ($-$16.9\,\pp average) due to CDict memory
overhead.  The remaining optimizations each contribute less than
1.5\,\pp individually, confirming that \sys's default configuration
is close to~optimal.

\subsection{Allocator Design Impact (RQ4)}
\label{sec:eval:allocator}

The previous experiments measure \sys end-to-end.  We now ask how
allocator design alone affects page compressibility, independent of
any compression pipeline.  For each of nine allocators, we run the
same application workloads used in RQ1---SQLite (50K rows,
no frees), memcached-format slab items, and Redis SDS strings
(100K objects each, 50\% freed in an
alternating pattern)---and compress the resulting heap pages with
zstd-9.

Table~\ref{tab:allocator_features} classifies each allocator by three
design properties relevant to compression: whether metadata (freelists,
bitmaps) is stored outside data pages, whether freed slots are
zeroed, and whether allocations are segregated by call site.

Figure~\ref{fig:allocator_compare} presents the compression ratios.
The results yield two observations.

First, zero-on-free is the dominant factor for page compressibility,
and its effect is workload-dependent.  Adding explicit zeroing before
\texttt{free} improves every allocator, confirming the effect is
causal.

Second, when frees are absent, allocator choice barely matters.
All allocators achieve similar compression because every byte on the
page is live, structured data.

\paragraph{Summary}
Zero-on-free is the single most important allocator design choice
for compressibility, with dramatic effects on data with low
byte-level redundancy and modest effects on text-heavy data.
When no frees occur, allocator choice is irrelevant.
These results motivate \sys's deferred zero-on-free: it captures the
compressibility benefit without adding latency to the
\texttt{free}~path.

\subsection{Pipeline vs.\ Allocator Design (RQ5)}
\label{sec:eval:pipeline}

Finally, we ask how much of \sys's benefit comes from the
compression pipeline versus its allocator design choices.
To decompose these contributions, we build a \emph{compress-only}
library
that adds \sys's compression pipeline \emph{on top of} the
unmodified system allocator.  This library interposes
\texttt{malloc}/\texttt{free} solely to discover which pages
belong to the heap; all allocation requests are forwarded to
system malloc unchanged.  It then applies \sys's page monitoring,
JIT compression (zstd-1$\to$zstd-9 tiering), signal-based
decompression, and prefetching to those pages.  Because allocation is still performed
by system malloc, pages contain embedded freelists, objects are
not zeroed, and allocations are not segregated by call site.
On Linux, the compress-only library discovers heap regions by
parsing \texttt{/proc/self/maps}.

glibc does not zero freed memory, so the compress-only
pipeline cannot achieve high compression ratios.
In fact, compress-only \emph{increases} RSS by 5--26\% due to
metadata overhead without corresponding compression~benefit.

Full \sys achieves 37--67\% reduction by combining allocator-level
page tracking with zero-on-free.  The allocator design contributes
most on RocksDB, where full \sys achieves 63\% reduction.
RocksDB's block cache entries span entire pages;
embedded freelist pointers from the system allocator degrade
compression across each page.

On Redis, compress-only achieves negative reduction (26\% overhead):
Redis's event loop touches heap pages even at minimum frequency
(\texttt{hz\,1}), so the pipeline's VM-region scanner never finds
cold pages to compress.  Full \sys avoids this problem because it
tracks page access internally at the allocator level.  With all
background tasks disabled (activedefrag, activerehashing, lazyfree),
full \sys achieves 36\% RSS reduction and 16\% lower AUC on Redis;
disabling these tasks does not affect the jemalloc baseline.
With the metadata-caching and idle-mode patches
described in \S\ref{sec:eval:apps}, \sys achieves 94\% RSS
reduction on Redis---comparable to memcached---because the
patches eliminate the two remaining sources of data-page warming
(defrag/rehash in \texttt{serverCron}) and data-page touching
(\texttt{getObjectLength} in \texttt{DEL}).

On memcached, compress-only shows 8\% overhead versus 67\%
reduction for full \sys; the gap reflects both \sys's zero-on-free
producing more compressible record pages and the allocator-level
tracking avoiding the VM region scanning overhead.

\paragraph{Summary}
The compress-only pipeline adds overhead rather than
reducing RSS because glibc does not zero freed memory.  Full \sys
achieves 37--67\% reduction by integrating the compression pipeline
with allocator-level page tracking and zero-on-free.  On Redis,
compress-only is ineffective because the event loop prevents pages
from going cold; full \sys's allocator-level tracking overcomes this.
The two components are complementary: the pipeline provides the
compression infrastructure, while the allocator design maximizes
its effectiveness on structured data.
