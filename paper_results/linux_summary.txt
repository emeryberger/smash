## Ablation Study (SQLite, --quick mode)
| Config            | RSS Reduction | Cold p50 (us) | Ops/sec |
|-------------------|---------------|---------------|---------|
| Default (B1)      | 65.9%         | 12.3          | 76.3K   |
| System malloc (B0)| 24.9%         | 1.2           | 84.7K   |
| With dicts        | 65.3%         | 12.4          | 77.5K   |
| No arenas         | 65.9%         | 13.0          | 75.7K   |
| LZ4 only          | 65.9%         | 12.1          | 77.1K   |
| No zero-deferred  | 65.9%         | 12.4          | 77.6K   |
| No prefetch       | 66.0%         | 25.5          | 76.4K   |
| Single worker     | 66.0%         | 13.3          | 76.7K   |
| No compression(B2)| 20.9%         | 8.7           | 76.9K   |

Key findings:
- Compression provides +45pp vs no compression (65.9% vs 20.9%)
- Smash provides +41pp vs system malloc (65.9% vs 24.9%)
- Prefetch reduces cold latency 2x (12.3us vs 25.5us)
- Dictionaries have minimal impact on Linux (-0.6pp)

## Compress-Only Experiment (SQLite)
| Config         | Cool RSS | Reduction |
|----------------|----------|-----------|
| Baseline       | 239 MB   | ---       |
| Compress-only  | 248 MB   | -3.8%     |
| Full Smash     | 131 MB   | 45.1%     |

Finding: Full Smash allocator design contributes significantly beyond just
compression pipeline. External metadata + arena routing essential for best results.

## Notes
- Linux uses 4KB pages vs macOS 16KB pages
- WKdm performs poorly on text data (word-granularity dictionary)
- LZ4 is optimal for cold pages: 30-37% ratio, ~1 GB/s compress, ~4-6 GB/s decompress
- zstd-9 gives best ratios but 6-10x slower than LZ4
- Smash's adaptive LZ4->zstd strategy optimal for mixed workloads
