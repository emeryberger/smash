\section{Evaluation}
\label{sec:eval}

We structure the evaluation around six questions:

\begin{enumerate}
\item[\textbf{RQ1.}] How do compression algorithms compare on heap
  page data?
\item[\textbf{RQ2.}] How much does \sys reduce RSS on real
  applications, and what is the throughput and latency cost?
\item[\textbf{RQ3.}] What does each optimization contribute?
\item[\textbf{RQ4.}] How does allocator design affect page
  compressibility?
\item[\textbf{RQ5.}] How much of the benefit comes from the
  compression pipeline versus the allocator design?
\end{enumerate}

\subsection{Methodology}
\label{sec:eval:method}

All experiments run on an Apple M1 Max (64\,GiB RAM,
16\,KiB page size, macOS~15).  \sys is loaded via dyld library
interposition; baselines use the system allocator.  Each
configuration is run three times; we report the median.
RSS is sampled via Mach task info at 100\,ms intervals.
We have also verified \sys on Linux aarch64 (Ubuntu~24.04,
glibc~2.39, 4\,KiB pages) via \texttt{LD\_PRELOAD}, where it
achieves 45--63\% RSS reduction on the same workloads.  Linux
results are comparable to macOS despite the 4$\times$ smaller
page size; Linux's \texttt{madvise} immediately releases
physical pages (versus macOS's lazy free), so RSS drops appear
more promptly after data goes~cold.

\paragraph{Memcached}
We load 500K TPC-H JSON records into memcached, then serve a hot 5\%
for 10 seconds before re-accessing cold keys.  Serve-phase RSS drops
from 240\,MiB to 180\,MiB (25\%) with no throughput difference (497
vs.\ 498 GET/s on the hot set).  Cold-key re-access is 54\% faster
(828K vs.\ 536K GET/s) because \sys prefetches adjacent pages on
fault.

\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{figures/memcached.pdf}
\caption{\textbf{Memcached RSS drops 25\% during serve as idle
  data compresses} (\S\ref{sec:eval:apps}).  Fill-phase RSS is
  higher due to metadata overhead.}
\label{fig:memcached}
\end{figure}

Fill-phase RSS is 11\% higher (260 vs.\ 233\,MiB) due to the
bootstrap allocator, page state arrays, and compression contexts.
This fixed overhead is amortized as the working set grows.

\paragraph{SQLite}
An in-memory database with 1M records queried with random lookups.
After cooling, RSS drops from 213 to 134\,MiB (43.8\% reduction).
Query throughput is 85K~ops/s, within 0.4\% of the baseline.

\paragraph{DuckDB}
TPC-H SF=0.5 queries against an in-memory columnar database.
Serve-phase RSS drops from 1372 to 939\,MiB (31.6\%) at identical
throughput (60~q/s).  Columnar storage produces large cold regions
as queries touch only a subset of columns.

\paragraph{RocksDB}
A 256\,MiB uncompressed block cache populated with 200K key-value
pairs.  Serve-phase RSS drops from 220\,MiB to 44\,MiB (80\%) at
941K ops/s.  RocksDB's built-in compression (LZ4 or zstd) reduces
data size on disk but not in the block cache, since blocks are
decompressed on load.  \sys and RocksDB compression are
complementary: they operate at different levels of the storage
hierarchy.

\paragraph{Redis}
200K JSON values.  Steady-state RSS drops from 56.8\,MiB to
46.9\,MiB (17\%) as idle data is compressed.

\paragraph{Comparison across allocators}
To confirm that compression, not allocator choice, drives the
RSS reduction, we run all five benchmarks with
Mesh~\cite{powers2019mesh} as a representative alternative allocator
(Table~\ref{tab:multi_alloc_apps}).  Mesh uses external metadata and virtual-memory
remapping to compact partially-filled pages.
On RocksDB, Mesh reduces RSS 35\% below system malloc (281 vs.\
434\,MiB) through meshing, and on DuckDB by 42\% (772 vs.\
1322\,MiB).  But \sys achieves 87\% on RocksDB (56\,MiB) and 31\%
on DuckDB (915\,MiB) via compression.
On the remaining three benchmarks, Mesh's RSS matches or
slightly exceeds system malloc:
meshing requires partially-filled pages with non-overlapping
occupancy, and these workloads keep most pages fully occupied.
Without a compression pipeline, even Mesh's aggressive page
remapping cannot reclaim space from pages with live objects.

700K keys with 240-byte values followed by 170K keys with
492-byte values, under a 100\,MiB LRU cap.  The size change
plus eviction creates partially-filled pages ideal for meshing.
We replicate this workload on our platform

Neither Mesh, jemalloc's activedefrag, nor \sys reduces RSS.
All configurations show the same $\sim$1.9$\times$ fragmentation ratio.
Three factors explain the discrepancy with the original result:
%
\begin{enumerate}
\item \textbf{Redis version.}  Powers et al.\ used Redis~4.0.2;
  we use 8.6.1.  Redis has substantially improved its internal
  memory management across five major versions.
\item \textbf{jemalloc version.}  The original used jemalloc~3.6.0;
  Redis~8.6.1 bundles jemalloc~5.3.0, which handles size-class
  transitions with much less fragmentation.
\item \textbf{Page size.}  macOS on Apple Silicon uses 16\,KiB pages
  versus 4\,KiB on x86 Linux.  Larger pages hold more objects per
  page, reducing external fragmentation: a page containing both
  240-byte and 492-byte objects is less likely to become a meshing
  candidate.
\end{enumerate}
%
The $\sim$1.9$\times$ fragmentation ratio reflects allocation
metadata overhead (SDS headers, dict entries, alignment padding),
not empty holes amenable to meshing or defragmentation.
This workload keeps pages fully occupied: LRU eviction frees
objects that are immediately replaced by new insertions,
leaving no partially-filled pages for Mesh to compact.
\sys's metadata overhead (page-state tracking, bootstrap
allocator) adds $\sim$15\,MiB, offsetting the small amount
of compression possible on this active dataset.

The most striking result is that enabling dictionaries
\emph{reduces} RSS savings by 5--30\,\pp across all benchmarks.
CDict objects consume 686\,KiB each at level~9, and at that
compression level, zstd's search window already captures the
patterns a dictionary would provide.  The dictionary adds only
frame overhead ($\sim$13 bytes) without improving ratios.  The
effect is worst on memcached ($-$24.5\,\pp) and Redis ($-$30.2\,\pp),
where the CDict memory overhead exceeds the small compressed-data
savings.  \sys therefore disables dictionaries by default
(\S\ref{sec:discussion}).

Disabling compression entirely ($-$45.7\,\pp average) confirms that
compression is the dominant mechanism; without it, \sys reduces to
a standard allocator with no RSS benefit beyond what the allocator
design alone provides.  The remaining optimizations---arenas, LZ4-only
mode, deferred zeroing, prefetch, and parallelism---each contribute
less than 1.5\,\pp individually.  RocksDB shows the largest marginal
effects (1--2\,\pp) because its 16\,KiB block cache entries span
entire pages, making per-page optimizations more visible.

\label{sec:eval:allocator}

allocator design affects page compressibility \emph{independently} of
the compression pipeline, we run a standalone benchmark that allocates

frees 50\% in an alternating pattern, and compresses the resulting
pages with zstd-9.  This experiment measures static page content compressibility.
Object sizes range from 64--512 bytes.

The results yield three observations.

First, zero-on-free is the single most important factor for page
compressibility.  Adding zeroing improves every allocator by 2--4\pp.
DieHard+zero matches DieHarder exactly (6.1\% average), confirming
that DieHarder's advantage over DieHard comes entirely from its
security zeroing, not from any other design difference.

Second, embedded freelists have a modest effect.
mimalloc, tcmalloc, and Hoard (9.5--9.6\%) compress $\sim$2\pp worse
than system malloc (7.4\%) without zeroing.  With zeroing, the gap
narrows to under 1\pp.  Freelist pointer pollution is measurable but
secondary.

Third, allocation layout matters more than metadata placement.
System malloc (7.4\%) compresses better than DieHard (10.1\%) despite
embedded freelists, because its sequential magazine layout produces
better locality.  DieHard's randomized placement scatters objects,
reducing page-level redundancy.  Mesh (7.9\%) confirms this: like
DieHard, it uses external bitmap metadata, but its layout is closer
to a conventional allocator, producing compressibility near system
malloc.  With zeroing, the relationship
inverts: DieHard+zero (6.1\%) compresses better because sparse
random pages have more zero space.  Mesh+zero (7.3\%) matches
system+zero, reinforcing that metadata placement is secondary
to layout and zeroing.

\subsection{Pipeline vs.\ Allocator Design (RQ5)}
\label{sec:eval:pipeline}

To decompose the contributions of the compression pipeline and
the allocator design, we build a \emph{compress-only} library
that adds \sys's compression pipeline \emph{on top of} the
unmodified system allocator.  This library interposes
\texttt{malloc}/\texttt{free} solely to discover which pages
belong to the heap; all allocation requests are forwarded to
system malloc unchanged.  It then applies \sys's page monitoring,
JIT compression (LZ4$\to$zstd tiering), signal-based decompression, and
prefetching to those pages.  Because allocation is still performed
by system malloc, pages contain embedded freelists, objects are
not zeroed, and allocations are not segregated by call site.

On macOS, system malloc uses Mach VM traps for heap regions,
which cannot be intercepted by dyld interposition.  The
compress-only library periodically scans VM regions using Mach's
region enumeration API, filtering for malloc-tagged anonymous
regions.  On Linux, it parses \texttt{/proc/self/maps}.

On SQLite and Redis, compress-only achieves \emph{higher} RSS
reduction than full \sys (47.5\% vs.\ 43.7\% and 49.2\% vs.\ 14.9\%,
respectively).  System malloc's sequential magazine layout can
produce more compressible pages for small objects than \sys's
arena-based layout, due to different alignment padding and object
clustering.  Redis shows the largest gap: its small, uniform values
compress well under any layout, but \sys's metadata overhead
(page-state tracking, arena routing) offsets the benefit for this
workload.  These results suggest that the relationship between
allocator layout and compressibility is workload-dependent rather
than monotonic.

On memcached, compress-only achieves 20\% reduction versus 25\%
for full \sys; the 5\pp gap reflects \sys's zero-on-free
producing more compressible record pages.

Compress-only incurs 7--18\% lower throughput on RocksDB
due to hash-map-based page tracking and periodic VM region
scanning.  \sys's integrated design avoids this overhead.
Redis and memcached show negligible throughput impact ($<$1\%)
for both configurations.
