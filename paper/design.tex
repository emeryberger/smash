\section{Design}
\label{sec:design}

\subsection{Design Overview}
\label{sec:design:arch}

\sys is designed around the principle that a memory allocator
possesses structural knowledge that dramatically improves page
compressibility.  A slab page may contain a mix of live objects and
freed slots holding stale data from previous occupants; the allocator
knows which slots are free and can zero them before compression.
Objects allocated from the same call site tend to have similar
structure; the allocator can route these allocations to dedicated
pages.  The allocator also tracks which size class occupies each page,
enabling per-size-class compression policies that skip data patterns
that do not compress well.  \sys exploits all three to achieve high
compression ratios with little impact on latency or throughput: it
defers zeroing of freed slots to compression time to
create compressible runs, routes allocations by call site to produce
homogeneous pages, and applies progressively stronger compression to
longer-idle~pages.

\sys is a slab-based allocator that interposes on \texttt{malloc},
\texttt{free}, \texttt{realloc}, and related functions via the alloc8
interposition framework~\cite{berger2025alloc8}, which uses
\texttt{DYLD\_INSERT\_LIBRARIES} on macOS and \texttt{LD\_PRELOAD} on
Linux.  Applications link against the system allocator normally; \sys
replaces it at load~time.

Figure~\ref{fig:heap_org} shows the heap organization and key data
structures; Figure~\ref{fig:arch} shows the page state machine.  The
allocator manages heap pages through a virtual memory region (up to
16\,GiB).  Each page transitions through five states:
(1)~\textbf{EMPTY}: never allocated or returned to the OS;
(2)~\textbf{ACTIVE}: contains live objects with full read/write
access;
(3)~\textbf{MONITORING}: marked read-only
(\texttt{PROT\_READ}) to detect future writes;
(4)~\textbf{COMPRESSING}: being compressed by a background worker;
and
(5)~\textbf{COMPRESSED}: compressed with zstd (level~1 or~9,
selected by ROI; \S\ref{sec:design:adaptive}), physical page
decommitted.

A background compressor thread wakes every second and executes three
phases (Figure~\ref{fig:arch}).  \emph{Phase~1} updates per-page
cold counts: for each active or monitored page, if the page was
accessed since the last tick its cold count resets to zero; otherwise
the count increments.  \emph{Phase~2} compresses pages whose ROI exceeds a
threshold, selecting the zstd compression level based on the cost--benefit
model (\S\ref{sec:design:adaptive}).  \emph{Phase~3}
marks all remaining ACTIVE pages read-only (\texttt{PROT\_READ}),
transitioning them to MONITORING.  This is how \sys detects writes:
when the application writes to a monitored page, a write fault fires,
the handler restores write permission and sets the page's access bit,
and the faulting instruction retries transparently.

Phase~3's per-tick \texttt{mprotect} is the most
frequent system call \sys issues.  Three factors keep its cost low.
First, contiguous active pages are coalesced into runs, so a heap
with thousands of active pages may require only a handful of
\texttt{mprotect} calls.  Second, hot pages fault immediately on
their next write, restoring \texttt{PROT\_RW} within
$\sim$1\,$\mu$s---no decompression, just a permission change---and
remain writable until the next tick.  Third, only pages tracked in
the chunk bitmap are visited, making the scan proportional to active
pages rather than the full VM region.  The net effect is negligible:
benchmarks show $\leq$0.4\% throughput overhead even on
write-intensive workloads (\S\ref{sec:eval:apps}).

When the application accesses a \emph{compressed} page, a page
fault signal fires.  The fault handler decompresses the page
(regardless of algorithm), resets its cold count to zero---analogous
to a JIT deoptimization---and returns, allowing the faulting
instruction to retry~transparently.

\subsection{Call-Site Arena Segregation}
\label{sec:design:arenas}

\sys uses 36 size classes with sub-linear spacing: every 16
bytes from 16--128\,B, then four classes per power-of-two group
(e.g., 160/192/224/256) up to 16\,KiB.  This spacing follows standard
allocator practice~\cite{berger2001composing}.  \sys maintains
four arenas (configurable as a power of two).  Each arena has
independent slab free lists for all 36 size classes in a flat
array indexed by arena and~class.

On each \texttt{malloc} call, \sys selects an arena using a
stack hash inspired by LLAMA~\cite{maas2020adaptive}:

\begin{lstlisting}
uintptr_t ra = return_address(0);
uintptr_t sh = frame_address(0);
uintptr_t h = ra ^ (sh >> 4) ^ size_class;
h ^= h >> 16;
arena = h & (kNumArenas - 1);
\end{lstlisting}

The hash combines three signals: the return address identifies the
immediate call site, the stack height (via the frame pointer)
distinguishes calls through different wrapper chains that share the
same immediate caller, and the size class adds object-type context.
This avoids walking the stack beyond depth~0, which would require
frame pointers and triggers compiler warnings.
Allocations from the same call site consistently land in the same
arena, producing structurally homogeneous page~content.

On \texttt{free}, the thread cache drains objects back to their
originating arena by looking up each pointer's span in the page map
and reading the span's \texttt{arena\_id} field.  This prevents arena mixing at deallocation~time.

\subsection{JIT Compression}
\label{sec:design:adaptive}

Just as a JIT compiler uses profiling data to decide which methods to
optimize and at what level, \sys uses per-size-class compression
statistics to decide \emph{whether} and \emph{how} to compress each
cold page.  The decision is driven by a \emph{return-on-investment}
(ROI) model that weighs the CPU cost of compression against the
expected RSS savings.

\paragraph{ROI model}
For each candidate page, \sys estimates two quantities.  The
\emph{cost} is the CPU time (in microseconds) to compress and later
decompress the page, which depends on both the algorithm and the data:
empirically, highly compressible data is cheaper to process, while
poorly-compressible data is slower.  \sys models throughput as a
linear function of the compression ratio, calibrated at startup by
compressing synthetic test pages (all-zeros and pseudo-random) with
each algorithm.  The \emph{benefit} is the RSS saved while the page remains
compressed: $\mathit{PageSize} \times (1 - R) \times E[T_{\mathit{remain}}]$,
where $R$ is the compressed-to-original ratio and
$E[T_{\mathit{remain}}]$ is the expected remaining cold duration.
Estimating $E[T_{\mathit{remain}}]$ requires a model of page idle
times.  Empirical studies of production
workloads~\cite{maas2020adaptive,amaro2023memory} show that page
inter-access times are heavy-tailed: most pages are either
frequently accessed or idle for long periods, with few in between.
For any distribution whose hazard rate $h(t) = f(t)/\bar{F}(t)$ is
non-increasing---a property called \emph{Decreasing Failure Rate}
(DFR), which holds for all heavy-tailed families including
Pareto, log-normal, and Weibull with shape~$< 1$---the expected
remaining lifetime given survival to~$N$ satisfies
$E[T - N \mid T > N] \geq E[T]$ and grows with~$N$.  For the
Pareto distribution specifically,
$E[T - N \mid T > N] = N/(\alpha - 1)$: the expected remaining
cold time is \emph{proportional} to the observed cold time.
\sys adopts this proportionality as a simple, conservative
model:
\[
\mathit{ROI} = \frac{\mathit{PageSize} \times (1 - R) \times N}
                     {\mathit{cost}_{\mathit{comp}} + \mathit{cost}_{\mathit{decomp}}}
\]
where $N$ is the cold count (ticks idle).  The model is
conservative because we use the \emph{already-observed} cold
duration~$N$ rather than a speculative future estimate, and
the proportionality constant is absorbed into the tunable ROI
threshold.  Because both cost terms increase with $R$ (worse
ratio $\to$ slower throughput) and the savings $(1 - R)$
decreases, the ROI is steeply sensitive to the compression
ratio.  Well-compressing pages (low $R$) have low cost and high
savings, so they are compressed early; poorly-compressing pages
(high $R$) have high cost and low savings, so they require a long
cold duration---or are skipped entirely.

\paragraph{Algorithm selection}
\sys uses zstd at two compression levels as a tiered strategy:
zstd-1 as the fast tier for recently-cold pages and zstd-9 as the
deep tier for long-idle~pages.  zstd-1 compresses at
$\sim$0.6--1.4\,GB/s---about 2$\times$ slower than LZ4---but
achieves 1.5--2$\times$ higher compression ratios
(Table~\ref{tab:algo_compare}), because its entropy coder (FSE)
captures byte-frequency skew that LZ4's literal-copy format cannot
exploit.  For cold pages that remain idle for seconds or minutes,
the better ratio (and thus greater RSS savings) more than
compensates for the additional compression~cost.
zstd-9 achieves a further 1.0--1.3$\times$ improvement over zstd-1
(Figure~\ref{fig:algo_compare}) at 10$\times$ lower compression
throughput, but comparable decompression speed (1.2--1.8\,GB/s).
\sys maintains throughput profiles for both tiers.  For each
candidate page, it computes the ROI for each and selects whichever
has the highest ROI above a configurable threshold.  Because zstd-9's
higher compression cost requires more cold ticks to amortize, the
fast tier dominates for recently-cold pages and zstd-9 wins only for
long-idle pages where the better ratio justifies the extra CPU\@.
This naturally produces tiered behavior without hard-coded
time~thresholds.  If the fast tier fails to compress below a
configurable ratio gate (default 75\%), \sys falls back to zstd-9,
which often achieves 30--50\% better compression on the same~data.

If a compressed page is accessed, it is decompressed and its cold
count resets to zero---analogous to a JIT deoptimization.  The page
will be recompressed only if it goes cold~again.

\paragraph{Auto-calibration}
At startup, \sys benchmarks zstd-1 and zstd-9 on two synthetic pages
(all-zeros and pseudo-random) to measure per-machine throughput,
taking the median of 10 iterations per algorithm per page
($\sim$1\,ms total).  The results populate the throughput profile
table.  On subsequent runs, calibration results can be cached to a
JSON file and reloaded, skipping recalibration.  Individual throughput
values and the ROI threshold can also be overridden via environment
variables, enabling tuning without recompilation.

\paragraph{Per-size-class statistics}
Not all size classes compress well.  \sys maintains a 64-entry sliding
window of compression ratios for each size class and worker.  The
window records the compressed-to-original ratio (0--255, mapping to
0--100\%) of each attempted compression.  These statistics feed the
ROI model: the average ratio from the sliding window serves as the
estimate of $R$ for future pages of the same size class.
With fewer than 8 samples, \sys falls back to optimistic compression
(compress anything past the cold-tick floor).  The sliding window
allows recovery: if data patterns change and new pages compress well,
old poor-ratio samples age~out.

\subsection{Lazy Free and Zero-on-Free}
\label{sec:design:zero}

\sys's \texttt{free()} is lazy: it returns the pointer to a
per-thread cache and returns immediately.  No
zeroing, no lock acquisition, and no interaction with the
compressor occur on the free path.  Freed slots are not reclaimed
by the slab until the thread cache drains a~batch.

Partially-filled slab pages therefore contain a mix of live objects
and freed slots.  Freed slots hold stale data from their previous
occupants, which lowers compression ratios.  \sys zeros freed
slots \emph{lazily at compression time}, replacing stale data with
zero runs that zstd compresses efficiently.

Before compressing a page, the compressor copies the page into a
scratch buffer, iterates the span's free bitmap to identify freed
slots, and zeros them using non-temporal stores
(\texttt{stnp}/\texttt{movnti}) to avoid cache pollution.  Deferring all zeroing to
compression time keeps the free path fast regardless of object~size.

\subsection{Scalability}
\label{sec:design:scalability}

\sys avoids global locks on the allocation fast path.  Each
application thread has a private thread cache that satisfies most
\texttt{malloc} and \texttt{free} calls without any synchronization.
When the cache must be refilled or drained, it accesses per-arena,
per-size-class slab free lists protected by fine-grained spinlocks;
four arenas spread contention across 144 independent lists ($4 \times
36$ size classes).  When a thread cache drains, freed objects are
returned to the global slab free lists (bucketed by arena), where any
thread can reuse them, avoiding memory
blowup~\cite{berger2000hoard} despite per-thread caching.  The
background compressor partitions work across parallel workers, each
with private compression state, and stores compressed data in an
8-shard pool to avoid serialization.  Signal-handler decompression
uses 32 pre-allocated fault slots acquired via compare-and-swap,
supporting 32~concurrent page faults with no shared mutable~state.
